# Adopt v1.1 engineering trust gates

- Status: accepted
- Date: 2026-08-27
- Owners: repository maintainers
- Scope: development quality, supported Python endpoints, CI aggregation, and
  GitHub Release publication
- Supersedes: none
- Superseded by: none

## Context

Hengmu already blocked tagged publication on its complete hosted matrix, but
the matrix exposed no stable summary result, covered only Python 3.11–3.13, and
did not enforce source coverage or strict static typing. Release publication
used one `gh release create` command, so a partial draft could not be resumed
safely and a repeated workflow had no explicit read-only published state.

## Decision

Support CPython 3.11–3.14. Run Python 3.11 and 3.14 on Ubuntu, macOS, and
Windows, and additionally run Python 3.12 and 3.13 on Ubuntu. The Ubuntu 3.13
lane owns branch coverage, changed-line coverage, and strict mypy; the Ubuntu
3.14 lane owns dependency vulnerability audit.

Aggregate the matrix and event-scoped dependency review into one `Quality gate`
job that always evaluates terminal results. Pull requests require dependency
review success. Push and tag events permit its expected skipped state, while a
failure or cancellation always blocks. Tagged release calls depend only on the
successful summary gate.

Set the `resources/scripts` runtime branch-coverage floor to 68% and collect
both runtime and maintainer `scripts` coverage for a 90% pull-request
changed-line floor. A changed file missing from coverage data fails closed.
Exclude only temporary extracted smoke-package paths. Keep JSON Schema as
runtime authority and use internal TypedDicts only after schema validation.

Publish Releases through two explicit modes:

- the tag workflow runs `prepare`; an absent Release becomes a draft, an
  existing draft may upload or replace only the six expected assets, and exact
  remote inventory, size, and SHA-256 digest must pass. This mode neither reads
  the repository immutable-release administration endpoint nor publishes;
- a local authenticated administrator runs `publish`. Its first remote
  administration check is the repository immutable-releases GET endpoint and
  requires a well-formed `enabled: true` response. Disabled, `404`, malformed,
  authentication, API, and CLI failures block with zero Release mutation;
- `publish` accepts only an already complete exact draft, never creates,
  uploads, or replaces assets, and performs the publish mutation once;
- after publish, a fresh Release readback must report `draft: false`,
  `immutable: true`, and the exact six-asset inventory before verification;
- an existing published Release is read and verified without mutation, and a
  mutable or malformed published response is rejected; and
- verification retries at most five times with ten-second intervals, after
  which repair requires a new patch release.

The six assets remain two ZIPs, their two checksum files, and two SPDX 2.3
SBOMs. Existing GitHub provenance and SBOM attestations remain authoritative;
no repository-managed signing key is introduced.

Before the first v1.1 tag, an administrator enables immutable releases and the
maintainer preserves an authenticated GET readback. The publication code never
uses PUT to enable the setting and cannot silently substitute workflow mutation
for that separately authorized administration step.

## Alternatives considered

- Run every Python version on every operating system — rejected because the
  intermediate versions do not prove an additional OS endpoint and would add
  four redundant jobs.
- Run `pip-audit` in every lane — rejected because all lanes consume the same
  exact runtime lock.
- Accept a skipped dependency review on pull requests — rejected because it
  would let the stable summary pass without its PR-specific supply-chain gate.
- Modify an already published Release after verification failure — rejected
  because published assets must be treated as immutable history.
- Add custom Ed25519 signing — rejected because it would introduce a separate
  key lifecycle without an identified offline verification requirement.

## Consequences

Pull requests gain deterministic type, coverage, workflow-state, and release
state-machine evidence. Hosted CI expands from seven to eight lanes. The tag
workflow prepares but does not publish the Release. A draft may safely resume;
the separately invoked local administrator publication phase cannot change its
assets and, once published, the Release can only be verified. Enabling
repository rulesets, tag rules, and GitHub immutable-release enablement remains
an explicit remote administration step with separately observed evidence. Once
enabled, every `publish` run fails closed unless its initial read-only API
preflight confirms the setting.

## Verification

- Run direct wrapper, migration-sentinel, changed-line Git-history, CI result
  table, and Release state-machine tests.
- Run strict mypy, branch coverage with XML output, full pytest, Ruff, all
  repository/knowledge/history/gate validators, dependency/license audit, and
  deterministic packaging twice.
- Observe the eight hosted lanes and stable summary gate before publishing a
  v1.1 tag.
- Before creating that first tag, record the administrator enablement and an
  authenticated immutable-releases GET response with `enabled: true`.

## Revisit when

- a supported Python endpoint reaches end of life;
- the same lock produces a platform-specific dependency audit difference;
- GitHub changes Release digest, immutability, or verification semantics; or
- an independent approver identity becomes available for repository rules.
